# ПОС — Преподавательская Оценка Студентов

ПОС - консольное приложение для выставления оценок студентам по критериям, расчёта итоговых результатов с учётом весов и экспорта результатов в CSV.

## 1. Возможности приложения

Приложение поддерживает следующие сценарии:

1. Добавление студентов (идентификатор - произвольная строка и имя)
2. Просмотр списка студентов 
3. Добавление критериев оценивания (идентификатор критерия, название, максимальный балл, вес)
4. Просмотр списка критериев
5. Выставление оценок студентам (Повторное выставление оценки студенту по одному критерию заменяет предыдущую оценку.)
6. Просмотр оценок конкретного студента
7. Удаление оценки 
8. Расчёт итоговой оценки с учётом весов критериев для одного студента
9. Расчёт итоговых оценок с учётом весов критериев для всех студентов
10. Экспорт итоговых результатов в CSV

## 3. Архитектура

Выбрана архитектура Ports & Adapters.

### Domain

Центральный слой, содержащий предметную область. Содержит Student, Criterion, Evaluation, Score, EvaluationFactory, TotalScoreService и WeightedAverageStrategy. Здесь поддерживаются инварианты: контролируется, что балл не выходит за пределы критерия, оценка создаётся только через фабрику и только по существующему критерию, итог считается в доменном сервисе. Domain не зависит от Application, Infrastructure, CSV, файловой системы или консоли.

### Application

Содержит сценарии использования приложения. POSFacade объединяет операции добавления студентов, критериев, выставления и отмены оценок, расчёта итогов и экспорта. Порты StudentRepository, CriterionRepository, EvaluationRepository и ResultExporter определяют контракты определяют контракты хранения данных и экспорта результатов. DTO StudentResult нужен для передачи данных между слоями: из application в infrastructure (CSV-экспорт) и в adapter (консоль).Application зависит от Domain, но не зависит от конкретных реализаций инфраструктуры.

### Infrastructure

Содержит технические реализации портов. memory реализует репозитории на map; оценки хранятся по составному ключу (studentID, criterionID), поэтому повторное выставление перезаписывает старую оценку. csv реализует экспорт итоговых результатов в CSV. При необходимости in-memory хранилище можно заменить другим хранилищем без изменения доменной модели.

### Adapter

Содержит консольный пользовательский интерфейс, получает пользовательский ввод, вызывает методы POSFacade и отображает результаты, но не рассчитывает итоговые оценки самостоятельно.

### Composition Root

Находится в internal/composition/container.go. Здесь создаются инфраструктурные компоненты, доменный сервис и POSFacade, после чего зависимости передаются через конструкторы. main.go только создаёт контейнер и запускает Runner.

### Направление зависимостей

cmd/pos -> Console Adapter -> Application -> Domain

Infrastructure -> Application ports -> Domain

cmd/pos зависит от Console Adapter; Console Adapter зависит от Application; Application зависит от Domain. Infrastructure зависит от портов Application и от Domain. Domain не зависит ни от кого. Composition Root (internal/app/container.go) собирает всё на краю, но ни один слой от него не зависит.

## 4. DDD

### Ubiquitous Language

В проекте используются термины предметной области:
- Student — студент.
- Criterion — критерий.
- Evaluation — оценка.
- Score — балл.
- Total Score — итоговая оценка.

Названия типов и методов в коде совпадают с этой терминологией: NewStudent, NewCriterion, TotalScoreService.Calculate и т.п.

### Entity

Student является Entity, потому что имеет уникальную идентичность (ID): два студента с одинаковым именем, но разными ID — разные. Criterion — Entity, потому что критерий имеет собственный ID, а его характеристики (название, максимум, вес) могут меняться без изменения идентичности. Evaluation — Entity, потому что представляет самостоятельный факт выставления оценки конкретному студенту по конкретному критерию.

### Value Object

Score — Value Object: он не имеет самостоятельной идентичности и определяется значением балла и максимально допустимым баллом. Создаётся только через NewScore, который проверяет диапазон 0 <= value <= max и отвергает NaN/Inf. Два Score с одинаковыми value и max равны. 

### Инварианты

Предметная область поддерживает следующие инварианты:

1. Идентификатор студента не может быть пустым.
2. Имя студента не может быть пустым.
3. Идентификатор критерия не может быть пустым.
4. Название критерия не может быть пустым
5. Максимальный балл критерия должен быть положительным.
6. Вес критерия должен быть положительным.
7. Выставленный балл не может быть отрицательным.
8. Выставленный балл не может превышать максимальный балл критерия.
9. Нельзя выставить оценку несуществующему студенту.
10. Нельзя выставить оценку по критерию, отсутствующему в списке критериев.


### Repository

Хранение вынесено за пределы домена. Порты StudentRepository, CriterionRepository, EvaluationRepository объявлены в application-слое, а реализуются в infrastructure (memory). Домен не знает, как и где хранятся данные; он работает только с сущностями и VO. Это позволяет менять механизм хранения без изменения бизнес-логики.

### Domain Service

TotalScoreService — доменный сервис, потому что правило расчёта итога зависит от нескольких сущностей: оно использует оценки студента и весь список критериев. Сервис принимает стратегию CalculationStrategy, что позволяет менять правило расчёта без изменения сущностей. Отсутствующая оценка трактуется как 0, totalWeight суммируется по всем критериям рубрикатора.


## 5. Паттерны GoF  

### Порождающие — Фабрика 

Структура: EvaluationFactory, метод Create. Это единая точка создания Evaluation: фабрика проверяет, что studentID не пуст, критерий существует и балл находится в пределах criterion.MaxScore(). Создать Evaluation в обход фабрики нельзя, потому что все поля приватные. Паттерн решает проблему создания некорректных оценок в обход доменных инвариантов: без фабрики проверку балла и связи с критерием пришлось бы дублировать в каждом сценарии, и была бы вероятность пропустить ее.

### Структурные — Facade

Структура: POSFacade. Фасад предоставляет единый интерфейс для сценариев приложения: добавить студента, критерий, выставить или отменить оценку, посчитать итог, собрать результаты, экспортировать. Консоль не взаимодействует напрямую с репозиториями, фабрикой и доменным сервисом — она вызывает только методы фасада. Паттерн решает проблему связанности UI с внутренним устройством приложения: без фасада консоль знала бы про FindByID, Save, Calculate и порядок их вызова, и любое изменение сценария ломало бы UI.

### Поведенческие — Strategy

Интерфейс: CalculationStrategy, реализация: WeightedAverageStrategy. Стратегия передаётся в TotalScoreService через конструктор, поэтому способ расчёта итога можно заменить, не меняя сервис и доменные сущности. Паттерн решает проблему сменяемого правила расчёта: если в дальнейшем понадобится другая формула, достаточно добавить новую реализацию CalculationStrategy и передать её в сервис. Без стратегии правило расчёта было бы зашито в TotalScoreService, и его изменение затрагивало бы доменный сервис.

## 6. Dependency Injection

Используется ручной DI - контейнер. Все зависимости создаются в internal/composition/container.go и передаются через конструкторы.

## 8. Тестирование

В условии задания и критериях оценивания упоминались только тесты на инварианты и Domain Service, поэтому юнит-тестами покрыт только модуль Domain.

## 9. Ограничения реализации

В консоли интерфейс над POSFacade не был реализован, так как в данном случае нигде не происходит подмена зависимостей: реализация одна, а тестов консоли с моками нет. Интерфейс здесь только дублировал бы список методов фасада. Поэтому консоль работает с конкретным *application.POSFacade. Если позже появится второй адаптер или понадобятся моки для тестов консоли, интерфейс можно будет объявить на стороне консоли.

## 10. Использование ИИ

ИИ использовался для написания юнит-тестов и сообщений к ошибкам.
